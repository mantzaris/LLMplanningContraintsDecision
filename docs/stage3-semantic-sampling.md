# Stage 3: solver-guided semantic sampling

This is an exploratory candidate-generation adaptation. Stage 2's consequence weighting did not improve on balanced selection; E remains paused. This stage compares independent sampling (A), a fixed source-focused perspective sequence (B), and the same sequence with executable-behavior feedback (C). It does not claim that diversity implies correctness.

All arms share the first two exact calls, common temperature 0.7, top-p 0.95, cached Qwen2.5-7B-Instruct, 768 output-token limit, and the existing schema. Subsequent B/C perspectives are frozen in `semantic_sampling.PERSPECTIVES`. C summarizes full acceptance signatures, repeated attempts, and separate top-level conjunct signatures over the entire public journey pool. A complete deterministic journey illustration is included only when it fits the 6,000-character feedback limit. Repetition is explicitly permitted. No references, ordinary judgments, or outcomes enter generation. Source associations use unique source operator/scope matches or unverified model spans; they are not semantic proof. Nested clauses without reliable associations remain available as whole conjuncts.

All arms use the source-only time-value normalization established in the Stage 2 diagnostic: an existing atom with a uniquely matching source phrase/operator/scope receives HH*3600+MM*60+SS. This does not insert omitted constraints or fix scope/operators/invalid JSON. Raw outputs and changes remain saved. The supported literal grammar is documented by the executable normalizer; it is an engineering baseline, not the contribution.

Generation trajectories finish before any prefix judging. Prefixes 2/4/8 use only their earlier attempts, syntax then exact bounded-behavior deduplication, existing solver/objective, balanced selection D, and at most two ordinary witness judgments. The existing judge prompt, renderer, deterministic tie-breaks and uncertain/all-eliminated behavior are unchanged. No repairs or new candidates arise during validation. Signature equality and candidate coverage mean agreement only within the checked pool, not unrestricted semantics or fidelity to the request.

## Development and resource rule (before development)

Use historical `pilot-00`, `pilot-17`, `pilot-34` only, checkpoints 2/4, with at most 64 actual calls; no parameter search. Temporary token limits: generation 48,000; validation 8,000 per prefix. Development is for integration, prompt sizes and runtime. Freeze fresh generation allowance at the next 1,000 tokens above `8*(maximum development translation input tokens + 768)`; validation per prefix at the next 1,000 above `2*(maximum development judgment input tokens + 768)`. If no ordinary judgment occurs, measure existing judge prompts with the same tokenizer without generation. The total per-request validation allowance is three such equal, nontransferable prefix allocations, identical in every arm. The primary final-prefix comparison uses its equal assigned generation and validation allowances; evaluating earlier prefixes incurs separately reported study overhead.

Admission uses exact tokenizer input size plus configured output maximum; successful calls consume actual input+output, failed calls with unknown output consume the full reservation. Duplicate calls are logically charged per arm/prefix even when actually cached. Exhaustion returns the output supported by available candidates. Shared/adaptive sample frequencies are not calibrated confidence.

Stage 3 has a separate append-only allocation: at most 1,500 actual requests and 7,200 GPU seconds including loading, warm-up, inference, retries and teardown. The measured guard is 7,080 seconds, reserving four possible 30-second uncertainty margins; no more than four sessions. Preserve historical 404 requests, 919.0111 measured seconds and at most 60 seconds uncertainty. A fresh 32-request upper forecast uses 38 calls/request (20 candidate, 18 judge), 1.5 times development p95 call latency, plus 120 seconds and 2 seconds/request; use 24 in fixed ID order only if 32 does not fit. If 24 cannot fit, stop before fresh evaluation. No interim outcome-based scope changes.

## Data and analysis rules

Construct 32 new provisional developer-authored requests from the existing frozen TriMet schedules: 10:00–13:00 on the same service day, excluding prior segment OD pairs and reversals. Reused routes/stops/date limit independence from earlier work. The fixed family cycle is timing/latest/transfer/timing/latest/transfer/scope/infeasible, repeated four times. Choose route round-robin, then least endpoint reuse, greatest scheduled ride coverage, then IDs. Use only clauses with both accepting and rejecting journeys and a conditional exclusion holding other clauses fixed. Establish genuine pool infeasibility independently. No mode/ordering requests are included because this bus-only subset does not provide meaningful coverage for them. The public universe is built before reference clauses and never pruned by them. Request grammar, independently evaluated clause coverage, explicit annotation-review CSV and rejection log are frozen before evaluation; none constitute independent human adjudication.

Primary outcomes at the common final allowance: any sampled interpretation matching the independently evaluated reference signature; and ordinary final-plan correctness. Retain every assigned request, including malformed outputs, false infeasibility, timeout, abstention and resource exhaustion. Report correct plans lacking full candidate equivalence separately. Offline oracle replay uses reference labels only in the diagnostic process and adds no calls. Base-request paired bootstrap intervals (10,000 draws) are exploratory; candidates/prefixes are not independent samples. One model and one replicate limit generalization.

**Continuation rule:** C must exceed both A and B by at least 10 percentage points in bounded correct-candidate coverage AND at least 5 points in ordinary final correctness at the final allowance. These are practical screening thresholds, not significance tests. No automatic next stage.

Figures plot actual consumption and observations: coverage versus generation tokens, correctness versus total logical tokens, candidate/journey heatmaps, and mutually exclusive missing-candidate/selection/other failure counts. Illustrations use first IDs exhibiting C-only coverage gain, a C failure, and a three-arm tie (deduplicated); if absent, first assigned ID. This deterministic choice is illustrative, not a representative sample.

## Closest overlap

[ARTEMIS (published ICSE 2026)](https://conf.researchr.org/details/icse-2026/icse-2026-research-track/287/Automating-Requirements-Formalization-Using-LLMs-and-Low-Complexity-Distinguishing-T) uses structured requirements, candidate specifications and low-complexity distinguishing traces for human semantic validation. Our balanced selector is an adaptation; this study changes candidate generation and uses automated judgments.

[Semantic Self-Verification (published IJCAI 2025)](https://www.ijcai.org/proceedings/2025/516) validates formalizations through concrete logical instantiations and solver checks. Repeated formalization and example-based validation are established components.

[Wang et al., sampling diversity (v5 preprint, August 2026)](https://arxiv.org/abs/2502.11027) studies inference-time diversification and source fidelity, motivating a credible prompt-diversification baseline. Prompt variation itself is not our proposed increment.

[VERGE (v2 preprint, May 2026)](https://arxiv.org/abs/2601.20055) directly overlaps: multiple formalizations, equivalence consensus, round-trip validation and solver-guided refinement. Our narrow adaptation feeds repeated finite-domain behaviors back into sampling, permits repetition rather than requiring strengthening, and controls perspective schedule and token allowances. This is a comparative investigation, not a claim to introduce formal-feedback loops.

The published patent application [US20250111220A1, “Sampling large language models with equivalence checking”](https://patents.google.com/patent/US20250111220A1/en) also describes equivalence checking, distinguishing discrepancies, prompt refinement and resampling. It is not a peer-reviewed empirical paper. Its overlap further rules out a broad novelty claim for equivalence-guided resampling. This targeted check is not exhaustive novelty verification or a legal assessment.

## Commands

Use the locked Python 3.11 environment. Prepare data with `python -m plancheck.sampling_data --feed data/raw/trimet-<sha256>.zip --output data/prepared/stage3`. Run with `python -m plancheck.sampling_run --config configs/sampling.json --public data/prepared/stage3/public --run runs/stage3-fresh --model-path /path/to/verified/cache`. Replay uses the same command with `--replay-from runs/stage3-fresh`, a new output directory, and no model path. The frozen protocol must match source/config/public hashes. GPU access instructions stay in local configuration; do not use another project's pod.
